# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"Küchengespräche" (kitchen-table conversations) — a minimal MCP server enabling **inter-session communication** between separate Claude Code sessions running on the same machine, so sessions can broadcast, poll, and ask/answer questions of each other like people chiming into a conversation without entering the room. Built per capability-centric DDD layering (`domain/` → `application/` → `infrastructure/` → `ui/`); no server process, no network — backed by a local SQLite file.

## Commands

```bash
python -m kitchen_chat_mcp                              # run the MCP server (stdio transport), from repo root
kitchen-talk-cli --room <room>                           # join a room as a human via a terminal TUI (needs `pip install -e .`)
python -m unittest discover -s tests -v                  # run the test suite (53 tests), from repo root
```

`kitchen_chat_mcp/__main__.py` calls `ui/server.py:main()`, which runs `anyio.run(run_server)` — `run_server()` opens `mcp.server.stdio.stdio_server()` and drives `mcp_server.run(...)` (the low-level `mcp.server.lowlevel.Server`, not FastMCP; see below).

## Architecture

```
ui → application → domain ← infrastructure
```

- `domain/Message.py` — `Message` (frozen dataclass: `room`, `sender_session_id`, `kind`, `content`, `in_reply_to`, `id`, `created_at`), `MessageKind` enum (`BROADCAST`, `QUESTION`, `ANSWER`, `PRESENCE`).
- `domain/MessageStore.py` — abstract store interface: `append`, `poll`, `get`, `find_answers`.
- `domain/Room.py` — `RoomInvariantError`; `Room.ensure_can_answer(question, existing_answers)` enforces that a question exists, belongs to the room, is actually a `QUESTION`, and has no existing answer.
- `domain/Subscription.py` — `Subscription` (frozen dataclass: `room`, `kind: MessageKind | None = None`); `matches(message)` returns true for same-room messages where `kind` is `None` (wildcard) or equal to the message's kind. Frozen + hashable so two subscriptions with the same `room`/`kind` compare equal and can share one watermark entry (see `ui/server.py` below).
- `domain/SubscriptionRegistry.py` — in-memory `add(subscription)` / `all() -> list[Subscription]` store, no persistence; lives for the lifetime of the server process.
- `application/PublishMessageUseCase.py` — `PublishMessageUseCase.execute(room, sender_session_id, content)`: appends a `BROADCAST` message.
- `application/PublishPresenceUseCase.py` — `PublishPresenceUseCase.execute(room, sender_session_id, content)`: appends a `PRESENCE` message (low-priority ping, e.g. "still here, nothing new"), kept distinct from real content so it doesn't drown out `BROADCAST`/`QUESTION`/`ANSWER` in a busy room.
- `application/PollMessagesUseCase.py` — `PollMessagesUseCase.execute(room, since_seq)`: delegates to `store.poll`; presence filtering happens in `ui/server.py`, not here (a display concern, not a domain rule).
- `application/AskQuestionUseCase.py` — `AskQuestionUseCase.execute(room, sender_session_id, question, timeout_seconds)`; appends a `QUESTION` message, then polls `find_answers` every `poll_interval_seconds` (default `0.5`) until an answer appears or `timeout_seconds` elapses, raising `AskTimeoutError`.
- `application/AnswerQuestionUseCase.py` — `AnswerQuestionUseCase.execute(room, sender_session_id, question_id, reply)`; loads the question and existing answers, checks `Room.ensure_can_answer`, then appends an `ANSWER` message.
- `application/ListRoomsUseCase.py` — `ListRoomsUseCase.execute()`: delegates to `store.list_rooms()`, used by the room picker in `ui/cli.py` (not exposed as an MCP tool).
- `application/SubscribeUseCase.py` — `SubscribeUseCase.execute(room, kind)`: builds a `Subscription(room=room, kind=kind)`, adds it to the injected `SubscriptionRegistry`, and returns it.
- `infrastructure/SqliteMessageStore.py` — WAL-mode SQLite `MessageStore` implementation, no server process. A partial unique index (`in_reply_to IS NOT NULL`) enforces "at most one answer per question" at the storage layer, closing the check-then-append race between `AnswerQuestionUseCase`'s read and its write — a second concurrent answer gets `sqlite3.IntegrityError`, translated to `RoomInvariantError`. `list_rooms()` returns distinct rooms that have at least one message, most recently active first (`GROUP BY room ORDER BY MAX(seq) DESC`).
- `infrastructure/RoomAllowlist.py` — `RoomAccessDenied`; `RoomAllowlist.ensure_allowed(room)` reads the `ROOMS` env var once at construction.
- `infrastructure/DbConfig.py` — `resolve_db_path()`: single source of truth for the `KITCHEN_CHAT_DB` env var / default-path resolution (and creates the parent dir), shared by every `ui/` adapter so they can never silently diverge onto different SQLite files.
- `ui/server.py` — built directly on `mcp.server.lowlevel.Server` (`mcp_server = Server("kitchen-talk")`), not FastMCP. FastMCP was tried first and rejected: its public API can neither declare the `claude/channel` experimental capability (`create_initialization_options()` is called internally with no way to pass `experimental_capabilities` through) nor hand back a live `ServerSession` to code outside an active tool call — both needed for the background-push feature this transport swap exists to prepare for (see `spike/channel_spike/RETRO.md`). `publish`, `poll`, `presence`, `subscribe`, `ask`, `answer` are plain undecorated functions with no framework dependency — this is deliberate so `tests/test_integration.py` can keep calling them directly as ordinary Python functions (see Testing gotcha below); they're wired into the MCP tool-call dispatch only via the `_TOOLS` name→function dict and the `@mcp_server.call_tool()` handler, which looks up `name` in `_TOOLS`, calls it synchronously (`_TOOLS[name](**arguments)`), and wraps the returned dict as `[types.TextContent(type="text", text=json.dumps(result))]`; `@mcp_server.list_tools()` returns hand-written `types.Tool` schemas from `_TOOL_SCHEMAS` (one dict per tool, matching each function's actual parameters/defaults) rather than something derived via `inspect.signature`, to keep the JSON Schema obviously correct by inspection. The `Server(...)` instance is named `mcp_server`, not `server`, because this module is itself conventionally imported and referenced as `server` elsewhere (`from kitchen_chat_mcp.ui import server`, then `server.publish(...)`, `server.store`) — naming the low-level `Server` instance `server` would collide with that. `store`/`allowlist`/`subscriptions` are lazily constructed on first use (via `_get_store()`/`_get_allowlist()`/`_get_subscriptions()`), not at import time — importing the module has no filesystem side effect, so it doesn't create a stray `kitchen-chat-mcp.db` just by being imported (e.g. by tests). Each tool calls `ensure_allowed(room)` first and translates domain/application exceptions into JSON-serializable `{"status": ...}` dicts rather than letting them cross the MCP boundary — `poll` hand-builds message dicts rather than returning `Message`/`MessageKind`/`datetime` objects directly.

  **Channel push mechanism.** `run_server()` calls `mcp_server.create_initialization_options(experimental_capabilities={"claude/channel": {}})`, declaring the `claude/channel` experimental capability in the `initialize` response unconditionally — every connection gets it, regardless of what the connecting client asked for; the server side of this negotiation isn't gated on a client-declared capability (see the `## Push notifications via Claude Code Channels` section below for what that means operationally). Reaching a *live* `ServerSession` from a background task (not from inside a tool call) has no public API in the `mcp` package, so the module swaps the `ServerSession` class that `mcp.server.lowlevel.server` references, at import time, for `_CapturingServerSession` — a subclass whose `__init__` stashes `self` into the module-level `_captured_session` dict; `mcp_server.run()` is otherwise called unmodified and ends up constructing this subclass itself, handing the module a reference to the session it would otherwise never see outside a tool-call `Context`. `run_server()` starts `_push_loop()` as a sibling task in the same `anyio` task group as the stdio serve loop (`tg.start_soon(_push_loop)`), and explicitly cancels the task group on the way out — `_push_loop` runs `while True` and is never cancelled on its own, so without the explicit `tg.cancel_scope.cancel()` after `mcp_server.run()` returns, shutdown would hang. Every `_POLL_INTERVAL_SECONDS` (env var `KITCHEN_TALK_POLL_INTERVAL_SECONDS`, default `3.0`), `_push_loop` calls `_collect_new_matches(subscriptions, store)`, a plain sync function (unit-tested with no live session at all, see `tests/test_channel_push.py`) that, per subscription: seeds its watermark via `_seed_watermark_if_new` if it doesn't have one yet, polls `PollMessagesUseCase` for messages after that watermark, applies the presence rule (a `PRESENCE`-kind message is only delivered to a subscription whose own `kind` is `PRESENCE` — never to a wildcard `kind=None` subscription — mirroring `poll`'s own default-off presence filtering), then `Subscription.matches()`, and advances the watermark to the highest seq seen regardless of match (so an unmatched message doesn't get re-scanned forever). Each match is sent via `_send_channel_notification`, which builds a raw `types.JSONRPCNotification(method="notifications/claude/channel", params={"content": ..., "meta": {"room", "kind", "sender_session_id", "message_id"}})` and writes it with `session.send_message()` — not `send_notification()`, which is typed to a closed Pydantic union (`ServerNotificationType`) that `notifications/claude/channel` isn't a member of and can't be added to without patching the `mcp` package itself; `send_message()` is the `mcp` package's own documented low-level/experimental escape hatch for exactly this (see `spike/channel_spike/RETRO.md`). `subscribe()` calls `_seed_watermark_if_new` itself, synchronously, at subscribe time, rather than leaving the first seed to `_push_loop`'s next tick — this was a real bug caught in review: a message published in the gap between `subscribe()` returning and the next `_push_loop` tick (up to `_POLL_INTERVAL_SECONDS` later) would otherwise be folded into that lazy seed's "current max as of now" and silently never pushed, even though it was published after the caller subscribed.
- `ui/cli.py` — `kitchen-talk-cli`, a Textual TUI for a human to join a room directly (no MCP, no extra process — opens the same `SqliteMessageStore` file directly). Two screens: `RoomPickerScreen` (shown when `--room` is omitted) lists rooms from `ListRoomsUseCase`, filtered through `RoomAllowlist.ensure_allowed` so a disallowed room is never offered; also accepts a typed name for a room with no history yet. Selecting/submitting a room pushes `ChatScreen`, which loads full history on start (`since_seq=0`) then polls every second via `PollMessagesUseCase`; `escape` pops back to the picker. Plain input publishes a `BROADCAST`; `/ask <question>` and `/answer <id-prefix> <reply>` drive `AskQuestionUseCase`/`AnswerQuestionUseCase` the same as the MCP tools do. Each rendered message is tagged with an 8-char id prefix; `_resolve_full_id` maps a typed prefix back to the full id, returning `None` on an ambiguous or unknown prefix rather than guessing. All blocking store calls run via `asyncio.to_thread` so the poll loop and input stay responsive.

### Testing gotcha

`tests/test_integration.py` calls the tool functions directly (not via MCP/stdio) and uses `unittest.mock.patch.object(server, "store", ...)` / `patch.object(server, "allowlist", ...)` per test to swap in a temp-dir SQLite db and a fresh allowlist, rather than reloading the module.

`tests/test_channel_push.py` additionally patches `server.subscriptions` (fresh `SubscriptionRegistry`) and `server._watermarks` (fresh `{}`) per test, on top of the same `store`/`allowlist` patches — both are module-level globals that would otherwise leak state (registered subscriptions, delivered-up-to watermarks) across tests.

## Configuration

| Env var | Default | Description |
|---|---|---|
| `KITCHEN_CHAT_DB` | `~/.kitchen-chat-mcp/kitchen-chat-mcp.db` | SQLite file path used by `SqliteMessageStore`. Fixed absolute default (not cwd-relative) so registrations that forget to set this still share one history instead of silently forking into a separate per-cwd database with its own independent `seq` sequence starting at 1 — which previously caused messages posted in one department to never show up when another polled, and made `seq` look duplicated/inconsistent across sessions. |
| `ROOMS` | unset | Comma-separated room allowlist. **Unset or blank means unrestricted — all rooms are allowed.** This is deliberate: the server works out of the box with zero configuration; set `ROOMS` only when you want to lock a deployment down to specific rooms. |
| `KITCHEN_TALK_POLL_INTERVAL_SECONDS` | `3.0` | How often the background `_push_loop` (see Architecture above) checks subscribed rooms for new messages to push via Channels. Read once at import time; only affects `subscribe`-based push delivery, not `poll`. |

## MCP tools

All six tools live in `kitchen_chat_mcp/ui/server.py`. Every tool first calls `allowlist.ensure_allowed(room)` and returns `{"status": "denied", "reason": ...}` if the room isn't in a configured allowlist.

| Tool | Signature | `status` values |
|---|---|---|
| `publish` | `publish(room: str, sender_session_id: str, content: str) -> dict` | `ok` (+ `message_id`) — broadcast stored; `denied` (+ `reason`) — room not allowed. |
| `poll` | `poll(room: str, since_seq: int = 0, include_presence: bool = False) -> dict` | `ok` (+ `messages`: list of `{seq, id, sender_session_id, kind, content, in_reply_to, created_at}`) — messages after `since_seq`, excluding `PRESENCE` messages unless `include_presence=True`; `denied` (+ `reason`) — room not allowed. |
| `ask` | `ask(room: str, sender_session_id: str, question: str, timeout_seconds: float = 30.0) -> dict` | `answered` (+ `content`, `sender_session_id`) — a reply arrived in time; `timeout` (+ `question`) — no reply within `timeout_seconds`; `denied` (+ `reason`) — room not allowed. |
| `answer` | `answer(room: str, sender_session_id: str, question_id: str, reply: str) -> dict` | `ok` (+ `message_id`) — answer stored; `rejected` (+ `reason`) — question doesn't exist, isn't a question, belongs to another room, or is already answered (`RoomInvariantError`); `denied` (+ `reason`) — room not allowed. |
| `presence` | `presence(room: str, sender_session_id: str, content: str) -> dict` | `ok` (+ `message_id`) — presence ping stored; `denied` (+ `reason`) — room not allowed. Use for low-priority "still here"/"nothing new" pings from a scheduled/cron poll loop, so they don't clutter `poll`'s default output. |
| `subscribe` | `subscribe(room: str, kind: str | None = None) -> dict` | `ok` — subscription registered (in-memory, for the life of this server process) and its watermark seeded to the room's current max seq, so only messages published after this call will be pushed; `rejected` (+ `reason`) — `kind` isn't a valid `MessageKind` value (`"broadcast"`/`"question"`/`"answer"`/`"presence"`); `denied` (+ `reason`) — room not allowed. See `## Push notifications via Claude Code Channels` below — `subscribe` only has any visible effect for a session launched with the right flag. |

`ask` posts its `QUESTION` message immediately, before it starts blocking/polling for an answer — only the wait is cancellable (e.g. by a timeout or the caller being interrupted), not the post. Use `publish` instead for anything non-urgent that shouldn't commit the session to blocking.

## Push notifications via Claude Code Channels

Claude Code has a research-preview "Channels" feature: an MCP server can push `<channel source="...">...</channel>` content into a session's *next turn*, without that session having polled for it. `subscribe(room, kind=None)` is how a session opts into this for kitchen-talk — it registers a `Subscription` in this server process's in-memory `SubscriptionRegistry`; a background loop (`_push_loop` in `ui/server.py`, see Architecture above) then checks every `KITCHEN_TALK_POLL_INTERVAL_SECONDS` for new matching messages and pushes each one as a `notifications/claude/channel` JSON-RPC notification.

**This requires launching the session with `claude --dangerously-load-development-channels server:kitchen-talk`** (`server:kitchen-talk` matches the MCP server name registered in `.mcp.json`). This flag is currently undocumented — it does not appear in `claude --help` — consistent with Channels being a research-preview feature (confirmed against CLI version `2.1.201`). The server side is verified by `spike/channel_spike/RETRO.md` at the protocol level: it unconditionally declares `capabilities.experimental["claude/channel"] = {}` in every `initialize` response and unconditionally sends the notification once a matching message exists, not gated on the client having passed the flag. **Live end-to-end delivery has since been confirmed manually** (2026-07-05, a real `post-production` department session launched with the flag): after that session called `subscribe`, a `publish` into the same room from a separate process arrived as a `<channel source="kitchen-talk">` block in its next turn.

**Operational gotcha, confirmed by that same manual test:** launching with the flag alone delivers nothing. `subscribe` must be called explicitly, once, inside that specific running session — the `SubscriptionRegistry` is in-memory and per-process, with nothing registered by default. The first live-test attempt produced no push at all until `subscribe` was called; only after that did the push loop have anything to match against. If a session launched with the flag doesn't seem to receive pushes, check first whether it (or something acting on its behalf) ever called `subscribe` for that room — that's a far more likely cause than a flag/registration problem.

`subscribe`/Channels is a pure addition, not a replacement: `publish`, `poll`, `presence`, `ask`, and `answer` all work exactly as before regardless of whether any session has subscribed or launched with the flag. `kitchen-talk-cli` (the human TUI) never touches `subscribe` or Channels at all — it stays polling-based (see `ui/cli.py` above) and has no reason to change.

## Concept & rationale

Background from the original design doc, `kuechengespraeche-inter-session.md` (German) — preserved here as rationale for decisions already made, not as a todo list. Likewise, `spike/channel_spike/` (`server.py`, `.mcp.json`, `RETRO.md`, `spike.log`) is a throwaway feasibility spike that predates and informed the Channels push mechanism (see `## Push notifications via Claude Code Channels` above) — not part of the production package, kept in place as the historical record of what was actually tested before the real implementation.

**Motivation.** Sessions need to interview each other or coordinate without a human relaying messages — e.g. a coding session asking a production session for context before implementing, or pre-production/production/post-production sessions exchanging state across session boundaries (see the film-production loop example in the doc). Two things already existed but didn't cover this:
- `RemoteTrigger`/`fire_trigger` fires a prompt into a specific session by `persistent_session_id`, but is one-way — no response channel.
- `ai-mem` is shared, readable-by-all memory, but push-free (polling only) and not built for blocking question/answer exchanges.

**Why SQLite over a broker daemon.** `claude-peers-mcp` (github.com/louislva/claude-peers-mcp) was evaluated and rejected: it covers bidirectional peer messaging and peer discovery, but requires a broker daemon (`localhost:7899`), a Bun runtime dependency, and potentially a claude.ai login for instant push — and it still has no channel-based `ask`/`answer` with blocking semantics, only peer-to-peer messages (the "wait for an answer" pattern would need to be rebuilt on top via polling anyway). This project instead uses a local SQLite file with no persistent process: sessions read/write directly, no daemon to keep running, no extra runtime dependency.

**Division of responsibility with ai-mem.** ai-mem holds persistent cross-session context; kitchen-talk is for ephemeral coordination between sessions that are active at the same time.

**Anticipated use.** SecurityCamera is gaining a webcam mode (HTTP API for camera control from the FP6 phone); once that lands, kitchen-talk is intended to act as the bridge between a filming session and the SecurityCamera session, following the same `publish`/`poll`/`ask`/`answer` pattern as the film-production loop example in the design doc.

## Adding a new MCP tool

1. If the new capability needs a new invariant or persistence method, add it to `domain/` first (e.g. a new abstract method on `MessageStore`, or a new rule on `Room`).
2. Implement any new persistence method in `infrastructure/SqliteMessageStore.py`.
3. Add a use case class in `application/` — one class per tool, taking a `MessageStore` in its constructor and exposing a single `execute(...)` method.
4. Wire it into `kitchen_chat_mcp/ui/server.py`: write it as a plain, undecorated function; call `_get_allowlist().ensure_allowed(room)` first, catch `RoomAccessDenied`/domain exceptions and translate them into a `{"status": ...}` dict; then add it to the `_TOOLS` dict and add a matching hand-written `types.Tool` entry to `_TOOL_SCHEMAS`.
5. Add tests: a use-case unit test (see `tests/test_use_cases.py`) and an integration test calling the tool function directly (see `tests/test_integration.py`), using `patch.object(server, "store", ...)` with a temp-dir SQLite db.
